1. *"งานวิจัยตอนขอตำแหน่งยังไม่มีให้เลือกเลย"* → มีสองสาเหตุซ้อนกัน **แก้ครบทั้งสองแล้ว**
   - **GAP-09**: เลือกตำแหน่งแล้ว **ไม่มีส่วนผลงานทางวิชาการโผล่ขึ้นมาเลย** เพราะ listener
     ถูกผูกกับ `<select>` ที่ถูกสคริปต์อื่นแทนที่ทิ้งไป — ทั้งช่องกรอกงานวิจัยและปุ่ม Scopus
     จึงถูกซ่อนอยู่ตลอด
   - **GAP-10**: ต่อให้ส่วนนั้นโผล่แล้ว กล่องรับผลงาน 11 กลุ่มก็มีปุ่ม "เลือกจาก Scopus" เพียง
     **3 กลุ่ม** และส่วนของ ผู้ช่วยศาสตราจารย์ ไม่มีปุ่มแม้แต่ปุ่มเดียว — ตอนนี้ครบทั้ง 11 กลุ่ม
2. *"ต้องเป็นงานวิจัยของคนคนนั้นเท่านั้น"* → **ทำถูกแล้ว** ฝั่ง server และ **GAP-13 แก้แล้ว**:
   ทางลัดที่เคยผูกกับบัญชีเริ่มต้นถูกย้ายไปอยู่ property ของตัวเองที่ปิดเป็นค่าเริ่มต้น
3. *"ยื่นไปแล้วใช้ยื่นซ้ำไม่ได้"* → **GAP-11/GAP-12 แก้แล้ว**: picker ส่ง publication id กลับมา
   กับฟอร์ม บันทึกลงตาราง `position_request_publication` และผลงานที่อยู่บนคำร้องที่พ้น `DRAFT`
   จะหายจาก picker และถูก API ปฏิเสธ — ยกเว้นคำร้องที่ถูกปฏิเสธ ซึ่งคืนผลงานให้ใช้ใหม่ได้

#### 🔴 GAP-04 — ทุก `@SpringBootTest` เดิม seed อีเมลจริงของบุคคลเป็น ROLE_ADMIN

> **ค้นพบระหว่างเขียนเทส** — ตาข่ายนิรภัยของชุดทดสอบใหม่ดักได้ทันทีในการรันครั้งแรก

`src/test/resources/application.properties` **แทนที่** (ไม่ใช่รวมกับ) `application.properties` ตัวหลัก
บน test classpath จึงไม่มีการตั้ง `app.admin.email` ระหว่างเทส และ `AdminInitializer` ตกไปใช้ค่า default
ที่เขียนไว้ใน `@Value`:

```java
// AdminInitializer.java:28
@Value("${app.admin.email:kriangkrai.p@kkumail.com}")
private String adminEmail;
```

ผลคือ **ทุกเทสที่ใช้ `@SpringBootTest` (36 คลาส) สร้างบัญชี `kriangkrai.p@kkumail.com` เป็น ROLE_ADMIN

#### ✅ GAP-46 — การกรองซ้ำไม่ตรวจภายในชุดที่กำลังเขียน — **แก้แล้ว**

`PublicationDeduplicator.findDuplicate()` ถามจากฐานข้อมูลอย่างเดียว ส่วน

เกิดขึ้นได้จริงเพราะ `PublicationHarvestService` รัน adapter ทุกตัว **ขนานกันด้วย virtual thread**

2. **ข้าม adapter ที่รันขนานกัน** — ล็อกการเขียนไว้ตัวเดียวตลอดทั้ง batch งาน harvest ติดคอที่เครือข่าย

```java
if (raw.title() != null && raw.title().length() >= 10 && raw.publicationYear() != null) {
    ... publicationRepo.findFuzzyMatchId(...)   // native similarity() ของ pg_trgm
} catch (Exception e) {
    log.warn("Fuzzy dedup query failed (pg_trgm extension active?): ...");   // กลืนไว้
}
```

การ `catch` ดูเหมือนปลอดภัย แต่ **transaction ถูกทำเครื่องหมาย rollback-only ไปแล้ว** ตอนที่ query ล้ม
ผลคือทั้ง batch ถูกยกเลิก โดยมีแค่ WARN บรรทัดเดียวในล็อก — ไม่มีอะไรบอกว่าข้อมูลไม่ได้ถูกเขียน
(พบตอนเขียนเทส: บน H2 ไม่มี `similarity()` งานเขียนทั้งชุดจึงหายทุกครั้งที่ชื่อเรื่องยาว ≥ 10 ตัวอักษร)

บน production ไม่พังเพราะ `V14` สร้าง extension ให้ แต่:
- ชุดทดสอบที่ใช้ H2 จะทดสอบเส้นทางเขียนของ harvest ไม่ได้เลย (เทสปัจจุบันเลี่ยงด้วยชื่อเรื่องสั้น)
- ถ้า query นี้ล้มชั่วคราวด้วยเหตุอื่น จะเสียทั้ง batch โดยไม่มีใครรู้

**แก้แล้ว:** คิวรีนี้ย้ายไปอยู่ใน `FuzzyTitleMatcher` ซึ่งเป็น bean แยกที่ประกาศ
`@Transactional(REQUIRES_NEW)` — transaction ของงานเขียนถูก suspend ไว้ ความล้มเหลวจึงทำเครื่องหมาย
เฉพาะ transaction ของตัวเอง batch ที่กำลังเขียนอยู่รอด และเสียแค่การเปรียบเทียบครั้งนั้นครั้งเดียว
นอกจากนี้ deduplicator จะ **ปิดชั้นนี้ถาวร**หลังล้มครั้งแรกพร้อม log อธิบายหนึ่งครั้ง แทนที่จะยิงคิวรี
ที่ล้มแน่ ๆ ซ้ำทุกแถวของทุก batch

ผลข้างเคียงที่ดี: `HarvestDeduplicationTest` ทดสอบเส้นทางเขียนจริงบน H2 ได้แล้ว (เดิมทำไม่ได้เลย)

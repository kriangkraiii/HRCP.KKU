# PLAN: ปรับลำดับขั้นตอนการติดตั้ง Digital ID (.p12) ก่อนการสร้างลายเซ็น (PLAN-p12-signature-flow.md)

## 1. ปัญหาและเป้าหมาย (Problem Statement & Goals)

### ปัญหาปัจจุบัน
- หน้า `/esign/my-signatures` วางส่วน "เพิ่มลายเซ็น" ไว้บนสุด ตามด้วย "ลายเซ็นที่บันทึกไว้" และนำส่วน "ใบรับรองดิจิทัล Digital ID (.p12)" ไปต่อไว้ด้านล่างสุดของหน้า
- ขัดกับตรรกะการทำงานจริง: การลงนามในระบบ KKU-HRCP จำเป็นต้องมีใบรับรองดิจิทัล Digital ID (.p12) ที่ถูกต้องเป็นข้อกำหนดหลัก (Prerequisite) หากผู้ใช้ยังไม่มี .p12 การสร้างลายเซ็นก็ยังไม่สามารถนำไปใช้ลงนามได้
- สำหรับผู้ใช้ที่ติดตั้ง .p12 เรียบร้อยแล้ว การ์ดใบรับรองดิจิทัลขนาดใหญ่ด้านล่างยังคงกินพื้นที่หน้าจอโดยไม่จำเป็น ทำให้หน้ารกและต้องเลื่อนจอมาก

### เป้าหมาย
1. กำหนดให้การติดตั้ง Digital ID (.p12) เป็นขั้นตอนแรก (Prerequisite Gate): หากยังไม่มีไฟล์ .p12 ที่ถูกต้อง หน้าจอต้องแสดงฟอร์มติดตั้งใบรับรองเป็นลำดับแรก และยังไม่เปิดให้สร้างลายเซ็น
2. เมื่อติดตั้ง .p12 เรียบร้อยแล้ว: ปลดล็อกหน้าจอสร้างลายเซ็นและแสดงรายการลายเซ็นที่บันทึกไว้เป็นพื้นที่หลัก
3. จัดวางปุ่มและส่วน "จัดการใบรับรองดิจิทัล (.p12)" ไว้อย่างเหมาะสมและเข้าถึงได้ง่าย (เช่น ปุ่มที่ส่วนหัว หรือแถบสถานะขนาดกะทัดรัด) โดยเปิดเป็น Modal หรือ Collapsible Card เพื่อไม่ให้รกพื้นที่หน้าจอ

## 2. การวิเคราะห์ทางเลือกสถาปัตยกรรม UI/UX (Brainstorming Options)

### ทางเลือกที่ 1 (Option A - แนะนำ): Prerequisite Gatekeeper + Header Status Chip & Modal
- **กรณีที่ยังไม่มี .p12 หรือ .p12 หมดอายุ:**
  - แสดงการ์ด "ขั้นตอนที่ 1: ติดตั้งใบรับรองดิจิทัล Digital ID (.p12)" โดดเด่นเป็นอันดับแรกที่ด้านบน
  - ซ่อนส่วนฟอร์มสร้างลายเซ็น หรือแสดงการ์ดล็อกพร้อมข้อความแจ้งเตือน "กรุณาติดตั้งใบรับรองดิจิทัลก่อน จึงจะสามารถสร้างลายเซ็นได้"
- **กรณีติดตั้ง .p12 เรียบร้อยแล้ว:**
  - แสดงแถบสถานะกะทัดรัด (Compact Status Bar) หรือ Chip บน Header:
    "สถานะ Digital ID: พร้อมใช้งาน ([ชื่อผู้ลงนาม] | หมดอายุ [วันที่])" พร้อมปุ่ม "จัดการใบรับรอง .p12"
  - เมื่อคลิกปุ่ม "จัดการใบรับรอง .p12" จะเปิด Modal สำหรับดูรายละเอียด, เปลี่ยนไฟล์ .p12 หรือยกเลิกการใช้งาน
  - พื้นที่หลักของหน้าจอแสดง "เพิ่มลายเซ็น" และ "ลายเซ็นที่บันทึกไว้" อย่างเต็มตา สะอาด และเป็นสัดส่วน
- **ข้อดี:**
  - ตรรกะถูกต้อง 100% ผู้ใช้ใหม่เข้าใจทันทีว่าต้องทำอะไรก่อน
  - หน้าจอสำหรับผู้ใช้ที่ติดตั้งแล้วสะอาด ไม่ต้องเลื่อนจอข้ามกล่องขนาดใหญ่
  - เข้าถึงการจัดการ .p12 ได้สะดวกจากทุกที่บนหน้า
- **ข้อจำกัด:**
  - ย้ายฟอร์มเปลี่ยนไฟล์ .p12 เข้า Modal
- **ระดับความซับซ้อน:** ปานกลาง

### ทางเลือกที่ 2 (Option B): Two-Step Tab Wizard (แท็บขั้นตอน)
- แบ่งหน้าเป็น 2 แท็บ:
  - แท็บ 1: "1. ใบรับรองดิจิทัล (.p12)"
  - แท็บ 2: "2. ลายเซ็นของฉัน"
- หากยังไม่มี .p12 จะล็อกแท็บ 2 ไว้ และเปิดแท็บ 1 เสมอ
- เมื่อติดตั้ง .p12 สำเร็จ จะสลับมาแท็บ 2 ให้อัตโนมัติ
- **ข้อดี:**
  - แยกบริบทของความปลอดภัยและรูปลักษณ์ลายเซ็นออกจากกันอย่างสิ้นเชิง
- **ข้อจำกัด:**
  - ผู้ใช้ต้องคลิกแท็บสลับไปมา และแท็บอาจทำให้หน้าดูล้าสมัย
- **ระดับความซับซ้อน:** ปานกลาง

### ทางเลือกที่ 3 (Option C): Conditional Inline Collapse (การ์ดด้านบนแบบพับเก็บได้)
- ย้ายการ์ด .p12 ขึ้นมาไว้บนสุด:
  - ถ้ายังไม่มี .p12: กางเต็มขนาด และซ่อนฟอร์มสร้างลายเซ็น
  - ถ้ามี .p12 แล้ว: ย่อเหลือเป็น Accordion/Collapse แถวเดียว พร้อมปุ่มกางออกเพื่อแก้ไข
- **ข้อดี:**
  - ปรับแก้ง่ายในโครงสร้าง HTML เดิม
- **ข้อจำกัด:**
  - เมื่อมี .p12 แล้ว ยังคงมีแถบคั่นอยู่ด้านบนก่อนถึงฟอร์มสร้างลายเซ็น
- **ระดับความซับซ้อน:** ต่ำ

## 3. แผนการดำเนินงาน (Task Breakdown)

### เฟส 1: ปรับปรุงเทมเพลต my_signatures.html
- เพิ่มการตรวจสอบเงื่อนไข `${activeCertificate != null && !activeCertificate.expired}`
- กรณีไม่มี .p12 หรือหมดอายุ:
  - แสดง Hero Card สำหรับการติดตั้ง Digital ID (.p12) ด้านบนสุด พร้อมคำแนะนำและฟอร์มตรวจสอบ/อัปโหลดไฟล์
  - ซ่อนหรือแสดงการ์ดล็อกสำหรับส่วนสร้างลายเซ็น
- กรณีมี .p12 สมบูรณ์:
  - แสดงปุ่ม "จัดการใบรับรอง .p12" พร้อม Badge สถานะที่ Header
  - เพิ่ม Modal `#p12ManageModal` สำหรับแสดงข้อมูลใบรับรอง, ปุ่มเปลี่ยนไฟล์ และปุ่มยกเลิกการใช้งาน
  - นำการ์ด .p12 ขนาดใหญ่เดิมออกจากด้านล่างของหน้าจอ

### เฟส 2: ปรับปรุง CSS และ JavaScript ใน esign.css
- ปรับแต่งสไตล์ของแถบสถานะใบรับรองกะทัดรัด (Certificate Status Bar / Chip)
- ปรับแต่งสไตล์การ์ดล็อกฟอร์มลายเซ็น (Locked State Card) ให้มีความชัดเจนและดูทันสมัย

### เฟส 3: ปรับปรุง Controller / Routing (หากจำเป็น)
- ตรวจสอบ `UserSignatureController.java`:
  - ตรวจสอบ flash message และ redirect parameter หลังอัปโหลด/ยกเลิกใบรับรอง เพื่อให้ Modal หรือหน้าจอแสดงผลได้ต่อเนื่อง
  - เพิ่ม URL parameter เช่น `?tab=cert` หรือ `?action=manageCert` เพื่อเปิด Modal ให้อัตโนมัติหากมีข้อผิดพลาด

### เฟส 4: การทดสอบและการยืนยันผล (Verification)
- เขียน Unit Test / Integration Test เพิ่มเติมใน `SigningPageRenderTest.java` หรือสร้าง Test ใหม่สำหรับหน้า `my_signatures`:
  1. ทดสอบกรณีผู้ใช้ยังไม่มี .p12: ต้องแสดงฟอร์มติดตั้ง .p12 เป็นลำดับแรก และซ่อนฟอร์มสร้างลายเซ็น
  2. ทดสอบกรณีผู้ใช้มี .p12 แล้ว: ต้องแสดงปุ่มจัดการ .p12, เปิดฟอร์มสร้างลายเซ็น และไม่แสดงการ์ดใหญ่ด้านล่าง
- รันแบบทดสอบทั้งหมดเพื่อป้องกันผลกระทบย้อนกลับ (Regression Testing)

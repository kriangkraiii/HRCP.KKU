## 2. การเข้าสู่ระบบ

ครอบคลุมทั้งการเข้าสู่ระบบด้วยรหัสผ่าน (UC-01) และการเข้าสู่ระบบผ่าน KKU SSO (UC-02) รวมถึงการยืนยันตัวตนสองขั้นตอน (UC-03) และการตั้งค่าบัญชีครั้งแรก (UC-04)

จุดสำคัญของกระบวนการนี้คือ **การยืนยันตัวตนไม่เท่ากับการได้รับสิทธิ์เข้าใช้ระบบ** เนื่องจาก KKU SSO ยืนยันตัวตนให้ผู้ใช้ทั้งมหาวิทยาลัย ระบบจึงต้องตรวจสอบรายชื่อที่อนุญาตซ้ำอีกชั้นหนึ่งตามลำดับ คือ สถานะการเปิดใช้งานบัญชี ทะเบียนบุคลากร รายชื่อที่กำหนดเพิ่มเติม และทะเบียนคณะกรรมการ หากไม่ตรงเงื่อนไขใดเลยระบบจะปฏิเสธการเข้าใช้งาน

![แผนภาพกิจกรรมการเข้าสู่ระบบ](diagrams/act-01-login.png)

## 3. การจัดทำและส่งคำร้อง

แสดงกระบวนการตั้งแต่ผู้ยื่นคำร้องสร้างคำร้องใหม่ จัดทำเอกสารทีละฉบับ แนบไฟล์ประกอบ จนถึงการส่งคำร้องเข้าสู่การพิจารณา

ระบบตรวจสอบเงื่อนไขก่อนอนุญาตให้ส่งคำร้องรวม 4 ข้อ ตามลำดับ

1. ผู้ใช้เป็นเจ้าของคำร้องนั้นจริง
2. คำร้องยังอยู่ในสถานะแบบร่าง
3. เอกสารบังคับจัดทำครบทุกฉบับ
4. เอกสารที่ต้องลงนามได้ลงนามครบถ้วนแล้ว

หากไม่ผ่านข้อใด ระบบจะยกเลิกการส่งและแจ้งรายการที่ยังขาดกลับไปยังผู้ยื่นคำร้อง

![แผนภาพกิจกรรมการจัดทำและส่งคำร้อง](diagrams/act-02-submit-request.png)

## 4. การลงนามเอกสารอิเล็กทรอนิกส์

เป็นกระบวนการที่ซับซ้อนที่สุดในระบบ เริ่มจากผู้ดูแลระบบสั่งเวียนเอกสาร ระบบอ่านผังลำดับผู้ลงนามของเอกสารประเภทนั้น จับคู่กับบุคลากรในทะเบียน แล้วสร้างซองเอกสารพร้อมขั้นตอนการลงนามทุกลำดับ

**กลไกสำคัญสามประการ**

**การบังคับลำดับการลงนาม** ขั้นตอนการลงนามมีสถานะแยกระหว่าง "รอคิว" กับ "ถึงคิวลงนาม" ระบบยอมรับลายเซ็นเฉพาะขั้นตอนที่อยู่ในสถานะ "ถึงคิวลงนาม" เท่านั้น และขั้นตอนจะเปลี่ยนเป็นสถานะนี้ได้ก็ต่อเมื่อทุกขั้นตอนก่อนหน้าลงนามครบแล้ว จึงไม่มีทางลงนามข้ามลำดับได้

**การแช่แข็งเนื้อหาเอกสาร** เมื่อเริ่มเวียนลงนาม ระบบจะบันทึกสำเนาเนื้อหาเอกสารพร้อมค่าแฮชไว้ และล็อกเอกสารไม่ให้แก้ไข ก่อนบันทึกลายเซ็นทุกครั้งระบบจะคำนวณค่าแฮชเทียบกับสำเนาที่แช่แข็งไว้ หากไม่ตรงกันแสดงว่าเนื้อหาถูกแก้ไขหลังส่งลงนาม ระบบจะเปลี่ยนสถานะซองเอกสารเป็น "ลายเซ็นเป็นโมฆะ" ทันที ซึ่งเป็นสถานะสิ้นสุดที่กู้คืนไม่ได้ เนื่องจากลายเซ็นที่ให้ไว้กับเนื้อหาคนละฉบับถือว่าไม่มีผล

**การเก็บหลักฐานการลงนาม** ทุกครั้งที่ลงนาม ระบบบันทึกเวลา หมายเลขไอพี ข้อมูลเบราว์เซอร์ รุ่นของข้อความยินยอม และค่าแฮชของเอกสารที่ลงนาม จากนั้นสร้างรหัสผนึกหลักฐานเพื่อให้ตรวจสอบย้อนกลับได้ผ่าน UC-32

![แผนภาพกิจกรรมการลงนามเอกสารอิเล็กทรอนิกส์](diagrams/act-03-signing.png)

## 5. การพิจารณาและปรับปรุงสถานะคำร้อง

แสดงการทำงานของผู้ดูแลระบบตั้งแต่ตรวจสอบคำร้องที่ได้รับ จนถึงการเลื่อนคำร้องไปยังขั้นตอนถัดไป โดยมีทางเลือกสามทางหลังการตรวจสอบเอกสาร คือ ส่งกลับให้แก้ไข ไม่รับพิจารณา หรือดำเนินการต่อ

เงื่อนไขสำคัญคือ **ระบบจะไม่ยอมให้เลื่อนสถานะหากเอกสารของขั้นตอนปัจจุบันยังลงนามไม่ครบ** ซึ่งเป็นการป้องกันไม่ให้คำร้องเดินหน้าไปโดยที่เอกสารประกอบยังไม่สมบูรณ์ตามระเบียบ

## 6. ระยะที่ 1 — การขอประเมินผลการสอน

แผนภาพภาพรวมของระยะแรก ตั้งแต่ผู้ยื่นคำร้องยื่นขอประเมินผลการสอน การแต่งตั้งคณะกรรมการประเมิน การนัดหมายวันประชุม จนถึงการแจ้งผลการประเมิน

ผลการประเมินแยกได้สามทาง คือ ผ่าน ให้แก้ไข และไม่ผ่าน เฉพาะกรณีผ่านเท่านั้นที่จะดำเนินการต่อไปยังระยะที่ 2 ได้ และระบบจะบันทึกวันหมดอายุของผลการประเมินเพื่อใช้แจ้งเตือนล่วงหน้าตาม UC-51

## 7. ระยะที่ 2 — การขอกำหนดตำแหน่งทางวิชาการ

แผนภาพภาพรวมของระยะที่สอง ตั้งแต่การจัดทำประวัติและแบบเสนอขอกำหนดตำแหน่ง การลงนามรับรองการมีส่วนร่วมในผลงานโดยผู้ประพันธ์ร่วม การพิจารณาของคณะกรรมการกลั่นกรองและคณะกรรมการวิทยาลัย จนถึงการส่งเรื่องไปยังกองทรัพยากรบุคคลของมหาวิทยาลัย

ลำดับสถานะในแผนภาพนี้ตรงกับสถานะของคำร้องที่ระบบกำหนดไว้ทั้งเจ็ดขั้น คือ รับคำร้อง ตรวจสอบความถูกต้องครบถ้วน เสนอวาระกลั่นกรองฯ รับรองมติกลั่นกรองฯ เสนอวาระคณะกรรมการวิทยาลัยฯ รับรองมติคณะกรรมการวิทยาลัยฯ และส่งออกกองทรัพยากรบุคคล มข. โดยมีสถานะแยกอีกสองสถานะคือ ส่งแก้ไข และไม่รับคำร้อง

## 8. หมายเหตุประกอบการจัดทำเอกสาร

1. ไฟล์ต้นฉบับของแผนภาพอยู่ในโฟลเดอร์ `docs/diagrams/` ชื่อไฟล์ขึ้นต้นด้วย `act-` เขียนด้วยภาษา PlantUML และมีไฟล์ภาพทั้งรูปแบบ PNG และ SVG
2. เมื่อแก้ไขไฟล์ต้นฉบับให้สร้างภาพใหม่ด้วยคำสั่งต่อไปนี้ โดยต้องกำหนดค่าขีดจำกัดขนาดภาพให้สูงขึ้น เนื่องจากแผนภาพกิจกรรมมีขนาดใหญ่กว่าค่าเริ่มต้นของโปรแกรม

```
java -DPLANTUML_LIMIT_SIZE=16384 -jar plantuml.jar -tpng docs/diagrams/act-*.puml
java -DPLANTUML_LIMIT_SIZE=16384 -jar plantuml.jar -tsvg docs/diagrams/act-*.puml
```

3. ไฟล์ `_style_activity.puml` เก็บรูปแบบร่วมของแผนภาพกิจกรรมทุกภาพ การแก้ไขไฟล์นี้เพียงไฟล์เดียวจะมีผลกับแผนภาพทั้งหมดพร้อมกัน
4. แผนภาพในหัวข้อที่ 4 มีขนาดใหญ่ที่สุด หากนำไปแทรกในเอกสารแล้วอ่านไม่ชัด แนะนำให้ใช้ไฟล์ SVG หรือจัดวางแบบเต็มหน้าในแนวนอน
5. เอกสารฉบับนี้แสดงกระบวนการหลักหกกระบวนการ ส่วนกระบวนการสนับสนุนอื่น เช่น การจัดการไฟล์ การซิงโครไนซ์ข้อมูลภายนอก และการแจ้งเตือนตามกำหนดเวลา สามารถอ้างอิงรายละเอียดได้จากคำอธิบายยูสเคสในเอกสาร [11-use-case-model.md](11-use-case-model.md) โดยไม่จำเป็นต้องจัดทำแผนภาพกิจกรรมเพิ่ม เนื่องจากมีลำดับการทำงานตรงไปตรงมาและไม่มีเงื่อนไขแตกแขนง

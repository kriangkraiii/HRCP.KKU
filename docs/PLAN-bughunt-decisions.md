## 1. วันหมดอายุผลประเมินการสอน (ต่างกัน 1 วัน)

**ตอนนี้:** `AcademicRequestService.expiryFromEvaluation` = วันประเมิน **+ 3 ปี − 1 วัน** (ประเมิน 2 ต.ค. 2569 → ใช้ได้ถึง 1 ต.ค. 2572)
ใช้ที่เดียวกันทั้งเซิร์ฟเวอร์ และ JS ในฟอร์มเอกสารที่ 9 (`templates/academic/admin/doc_fragments/9.html` → `calculateExpiry`)

**ข้อเท็จจริงที่เจอ:**
- กติกานี้ทีมตั้งใจเลือก (commit `751711e`, 2 ต.ค. 2569 — "+3 years minus 1 day") ไม่ได้พลาด
- แต่คอมเมนต์ทั้งใน Java และ JS อ้างว่า "นับตาม ป.พ.พ." ซึ่งไม่ตรง: ม.193/3 ไม่นับวันแรก (เริ่ม 3 ต.ค.) + ม.193/5 สิ้นสุดวันก่อนวันที่ตรงกับวันเริ่ม = **2 ต.ค. 2572**
- กติกา −1 วัน ตรงกับแบบที่หน่วยงานรัฐหลายแห่งใช้กับใบอนุญาต (นับวันออกเป็นวันแรก) — จึงเป็นเรื่องนโยบาย ไม่ใช่บัคชัด ๆ
- ประกาศ 1669/2569 เขียนแค่ "มีอายุ 3 ปี นับจากวันประเมินการสอน"

| ทางเลือก | ผล | งาน |
|---|---|---|
| ★ **A. คงกติกาเดิม** | หมดอายุเร็วกว่า 1 วัน — ไม่มีใครใช้ผลที่หมดอายุแล้วได้ | แก้คอมเมนต์ 2 จุดให้บอกเหตุผลจริง ("นับวันประเมินเป็นวันแรก") ไม่อ้าง ป.พ.พ. |
| B. นับตาม ป.พ.พ. | ใช้ได้ถึงวันที่ตรงกัน (2 ต.ค. 2572) | เปลี่ยน `expiryFromEvaluation` + `calculateExpiry` (JS) + คอมเมนต์ + `DocumentFieldOwnershipTest` |

**ข้อมูลเดิม (ถ้าเลือก B):** หนังสือแจ้งผล (เอกสารที่ 9) ที่ลงนามแล้วพิมพ์วันหมดอายุไว้ใน JSON (`expiration_date`) — ลำดับการหาวันหมดอายุ (`resolveExpiry`, `getLatestEvaluationExpiry`) ใช้ค่าที่พิมพ์ก่อนเสมอ จึง**ไม่เปลี่ยน**ย้อนหลังเอง ฉบับที่ยังไม่ลงนามคำนวณใหม่ตอนบันทึก/แสดง (`withDerivedExpiry`) → ไม่ต้องมี migration

**ตัดสินแล้ว (16 ต.ค. 2569) → ทางเลือก A:** HR ฉบับกระดาษนับจาก "ผลออก" = วันประชุมกรรมการประจำวิทยาลัยฯ รับรองผล (เอกสารที่ 8 `meeting_date` — ที่ระบบใช้เป็น `evaluation_date` อยู่แล้ว)
และพิมพ์แบบ −1 วัน (ผลออก 2 ต.ค. 2569 → หมดอายุ 1 ต.ค. 2572) — **ตรงกับระบบทุกอย่าง** งานเหลือแค่แก้คอมเมนต์ใน `expiryFromEvaluation` และ `calculateExpiry` (JS) ให้อ้างแนวปฏิบัติของ HR แทน ป.พ.พ.

**เทส:** A — ไม่มี (คอมเมนต์อย่างเดียว) / B — ทดสอบ 2 ต.ค. 2569 → 2 ต.ค. 2572, 29 ก.พ. → 28 ก.พ./1 มี.ค. (ปีอธิกสุรทิน), และ JS ให้ผลเท่ากับ Java

**ขนาดงาน:** A ~10 นาที / B ~1 ชม.

## 2. ข้อมูลเดิมที่ผิดจากบัคที่แก้ไปแล้ว

### 2a. เอกสารที่ 7 ที่คะแนนรวม 56 / 71 / 86 พอดี (บัค #4)

**ทำไมสำคัญ:** `eval_result_level` ที่บันทึกไว้ตัดสินสถานะจริง — `autoUpdateStatusByDocument` (case 7) ใช้ตัดสิน `SUBCOMMITTEE_FAIL` / `COMPLETED_PASS`, ถูกยกไปเป็น `result_level`/`is_qualified` ในหนังสือแจ้งผล (เอกสารที่ 9) และใช้ตัดสิทธิ์ยื่นขอตำแหน่ง (`levelShortfall`)
ก่อนแก้ คะแนน 56.00 พอดีอาจถูกคิดเป็น 55.999… → **"ไม่ผ่าน"** ทั้งที่ผ่าน (71 → ได้ "ชำนาญ" แทน "ชำนาญพิเศษ" = ไม่ถึงเกณฑ์ รศ.)

**ลายเซ็นของบัคในข้อมูล:** `scorex` = `56.00`/`71.00`/`86.00` แต่ `eval_result_level` เป็นระดับที่ต่ำกว่าหนึ่งขั้น — หาได้ตรง ๆ ด้วย SQL (ภาคผนวก Q1)

**แผน:**
1. รัน Q1 บน production (อ่านอย่างเดียว) — **ถ้าได้ 0 แถว จบเรื่องนี้**
2. ถ้ามีแถว: ทำรายการ (รหัสคำร้อง, สถานะ, ลงนามแล้วหรือยัง) ให้ HR ตัดสินรายคน
   - เอกสารที่ 7 ยังไม่ลงนาม → เจ้าหน้าที่กดบันทึกซ้ำ ระบบคำนวณใหม่ด้วยสูตรที่แก้แล้ว
   - ลงนาม/แจ้งผลไปแล้ว → เป็นเรื่องออกหนังสือใหม่หรือให้ขอทบทวน (นอกระบบ) — ระบบไม่แก้ให้เอง
3. ★ (ตัวเลือก ~30 นาที) แถบเตือนบนหน้าเอกสารที่ 7 ฝั่งแอดมิน เมื่อระดับที่บันทึกไม่ตรงกับคะแนนรวม (`Doc7Scoring.evalLevelFromScore(scorex)`) — กันกรณีที่ SQL พลาดไป

### 2b. ผลงานตีพิมพ์ซ้ำที่อยู่ในฐานข้อมูลแล้ว (บัค #30)

**ทำไมสำคัญกว่าแค่แสดงซ้ำ:** ตัวเลือกผลงานซ่อน "ผลงานที่ใช้ไปแล้ว" ด้วย id (`position_request_publication`) — ผลงานชิ้นเดียวมี 2 แถว ใช้แถว A ไปแล้ว แถว B ยังโผล่ให้เลือก → **ยื่นผลงานเดิมซ้ำในคำร้องอื่นได้** (ผิดกติกา "งานหนึ่งชิ้นใช้ได้ครั้งเดียว" จนกว่าสภาฯ มีมติ)

**สิ่งที่อ้าง id ของผลงาน:** `position_request_publication.publication_id`, JSON เอกสารที่ 1 (`*_scopus_id_N`), ดัชนีค้นหา (PUBLICATION)

| ทางเลือก | สรุป |
|---|---|
| ★ **A. รวมแบบนุ่ม (soft-merge)** | เพิ่มคอลัมน์ `merged_into_id` — แถวที่ถูกรวมยังอยู่ (id เดิมใน JSON ยังเปิดได้) แต่หายจากทุกรายการ |
| B. รายงานอย่างเดียว | หน้าแสดง "อาจซ้ำ" ให้แอดมินดูเอง — ไม่ปิดช่องโหว่ใช้ซ้ำ |
| C. ไม่ทำ | ป้องกันแค่ข้อมูลใหม่ (ทำแล้วใน #30) |

**งาน (ทางเลือก A):**
1. Migration `V48__publication_merged_into.sql` — `ALTER TABLE scopus_publication ADD COLUMN merged_into_id BIGINT` + index
2. ทุก query ที่แสดง/ค้นหา/กรองซ้ำ ข้ามแถวที่ `merged_into_id IS NOT NULL`: ตัวเลือกผลงาน (`findOwnedBy*`), หน้าแอดมิน, `PublicationDeduplicator` (DOI/hash/fuzzy), `SearchDocumentLoader`
3. `PublicationMergeService`:
   - จับคู่ภายในเจ้าของเดียวกัน ด้วย DOI แล้วด้วย `dedup_hash` (ไม่ใช้ fuzzy — รวมผิดแล้วแก้ยาก)
   - แถวที่เหลือ = แถว `SCOPUS` (FS sync อัปเดตต่อด้วย eid จริง)
   - ย้าย `position_request_publication` ไปแถวที่เหลือ (ชน unique `(request_id, publication_id)` → ลบลิงก์ซ้ำ)
   - `syncPublicationLinks` แปลง id ที่ถูกรวมเป็น id ที่เหลือ — บันทึกเอกสารที่ 1 ครั้งหน้าไม่สร้างลิงก์ไปแถวเก่าอีก
   - บันทึกลง admin log ทุกคู่
4. หน้า "ซิงก์ข้อมูลภายนอก": ปุ่ม **ตรวจหาผลงานซ้ำ** → แสดงรายการคู่ (dry-run) → **ยืนยันรวม**

**ลำดับเวลา:** deploy #30 ก่อน แล้วรอ FS sync รอบกลางคืน 1 รอบ (แถว Scopus ได้ `dedup_hash` ครบ) ค่อยรันการรวม — ไม่อย่างนั้นจับคู่ได้แค่ด้วย DOI

**ข้อมูลเดิม:** รัน Q2 ก่อนเพื่อดูจำนวนคู่ ถ้าน้อยมาก (เช่น < 10) ทางเลือก B/ลบมือก็พอ

**เทส:** คู่ DOI/hash ถูกรวม, คู่ Scopus–Scopus ไม่ถูกรวม, ลิงก์ย้ายตาม + ชน unique, ตัวเลือกไม่แสดงแถวที่ถูกรวม, ผลงานที่ใช้แล้วยังนับว่าใช้แล้วหลังรวม

**ขนาดงาน:** ~1 วัน

## 3. สิทธิ์ (role) ที่แอดมินตั้งได้

**ตอนนี้:**
- `update-user` / `update-admin` / `save-admin` รับ `role` จากฟอร์มตรง ๆ (`UserServiceImpl.updateUserDetails`, `saveAdmin`) — POST ค่าอะไรก็ได้
- แอดมินเปลี่ยน role ของตัวเองได้ (ลบ/ระงับตัวเองไม่ได้แล้ว — #42)
- **ช่องโหว่ที่เจอเพิ่ม:** `SigningController` (4 จุด) และ `SignerOptionDTO` ถือ `ROLE_STAFF` เท่ากับแอดมิน แต่ไม่มีฟอร์มไหนให้เลือก และ `SecurityConfig` ไม่รู้จัก → POST `role=ROLE_STAFF` สร้างบัญชี "ครึ่งแอดมิน" ที่เปิดตัวอย่าง/ลายเซ็นของซองใดก็ได้
- role แปลก ๆ อื่น → บัญชีเข้า `/user/**` ไม่ได้เลย (ล็อกตัวเองออก)

**แผน (★ ทำทั้งหมด):**
1. Whitelist ที่เดียวใน `UserServiceImpl`: `ROLE_USER`, `ROLE_ADMIN`, `ROLE_EXTERNAL` (ตรงกับตัวเลือกในฟอร์ม) — ค่าอื่นปฏิเสธพร้อมข้อความ
2. แอดมินเปลี่ยน role ตัวเองไม่ได้
3. ลดสิทธิ์/ระงับ **แอดมินคนสุดท้ายที่ยังใช้งานได้** ไม่ได้ (ครอบ `updateSts` ด้วย)
4. `ROLE_STAFF`: รัน Q3 ก่อน — ถ้าไม่มีบัญชี STAFF → ลบเงื่อนไข STAFF ออกจาก `SigningController`/`SignerOptionDTO` (โค้ดตาย + ช่องยกสิทธิ์) / ถ้ามี → ต้องตัดสินว่าจะย้ายเป็น ADMIN หรือ USER

**ตัดสินแล้ว (16 ต.ค. 2569):** ROLE_STAFF ไม่เคยตั้งใจให้มี → ลบเงื่อนไข STAFF ออกจาก `SigningController`/`SignerOptionDTO` และไม่อยู่ใน whitelist (ถ้า Q3 เจอบัญชี STAFF ค่อยย้ายเป็น USER/ADMIN ตามคน)

**เทส:** role นอก whitelist ถูกปฏิเสธ (ทั้ง 3 endpoint), เปลี่ยน role ตัวเองไม่ได้, แอดมินคนสุดท้ายลดสิทธิ์/ระงับไม่ได้, แอดมินคนอื่นยังลดสิทธิ์กันได้

**ขนาดงาน:** ~2 ชม.

## 4. ซิงก์จากเว็บคณะเขียนทับคำนำหน้าชื่อ

**ตอนนี้:** `CpDirectorySyncService.applyUserDetails` เรียก `AcademicTitleResolver.resolveShortTitle(เว็บก่อน…, คำนำหน้าเดิมท้ายสุด)` แล้ว**เขียนทับ**ทุกวันอาทิตย์ (ยกเว้นบัญชีที่ SSO ยืนยันตำแหน่ง) — ขณะที่ Javadoc ของคลาสบอกว่า "เติมเฉพาะช่องว่าง"
**เจตนาเดิม** (commit `f13a322`): ยกระดับคำนำหน้าจาก HR feed ("นาย") เป็น "ผศ.ดร." — ใช้ได้ดี
**ปัญหา:** เว็บคณะอัปเดตช้า — คนที่เพิ่งได้ รศ. และแอดมินแก้เป็น "รศ.ดร." แล้ว จะถูกดึงกลับเป็น "ผศ.ดร." ทุกสัปดาห์ (ตำแหน่งจากเว็บมาก่อนในลำดับ) → ชื่อที่พิมพ์ในเอกสารราชการผิด

| ทางเลือก | ผล |
|---|---|
| A. เติมเฉพาะช่องว่าง (ตาม Javadoc) | ไม่ทับอะไรเลย — แต่ "นาย" จาก HR feed จะไม่ถูกยกเป็น "ผศ.ดร." อีก |
| ★ **B. ยกระดับได้ ลดไม่ได้** | ทับเมื่อเว็บแสดงตำแหน่ง**สูงกว่าหรือเท่ากัน** (ยังเติม "ดร." ได้) ถ้าเว็บต่ำกว่า → ข้าม และนับไว้ในผลซิงก์ |
| C. B + ยึดตำแหน่งที่สภาฯ อนุมัติในระบบ (`approvedRankOf`) เป็นพื้น | แน่นที่สุด แต่ซับซ้อนกว่า |

**งาน (B):** ใน `applyUserDetails` เทียบ `AcademicRank.of(คำนำหน้าเดิม, academicPosition)` กับ `AcademicRank.of(ค่าจากเว็บ)` ด้วย `isAbove` (มีอยู่แล้ว) + เพิ่มยอด "ข้าม — เว็บแสดงตำแหน่งต่ำกว่าในระบบ N คน" ใน `Result.describe()` + แก้ Javadoc ให้ตรง

**ข้อมูลเดิม:** คำนำหน้าที่ถูกลดไปแล้วตรวจย้อนได้บางส่วน — Q4 หาคนที่คำนำหน้าต่ำกว่า `academic_position` ในระบบ

**เทส:** "รศ.ดร." + เว็บ "ผศ.ดร." → คงเดิม; "นาย" + เว็บ "ผศ.ดร." → "ผศ.ดร."; "ผศ." + เว็บ "ผศ.ดร." → "ผศ.ดร."

**ขนาดงาน:** ~1 ชม.

## 5. เอกสารระเบียบที่ HR ถอดออกจากเว็บแล้วยังค้างในระบบ

**ตอนนี้:** `KkuDocumentSyncService.syncNow` เพิ่ม/อัปเดตอย่างเดียว ไม่เคยเอาออก → ระเบียบที่ถูกยกเลิก (เช่นชุด 2565 ที่ถูกแทนด้วย 2569) ยังขึ้นในหน้าคลังเอกสารและผลค้นหา
มีธง "ซิงก์ครบ" อยู่แล้ว (`failures.isEmpty()`) ใช้เป็นเงื่อนไขได้

| ทางเลือก | ผล |
|---|---|
| ★ **A. ถอดแบบนุ่ม** | คอลัมน์ `retired_at` — ซ่อนจากหน้าและการค้นหา ถ้า HR ใส่กลับ ก็กลับมาเอง |
| B. ลบจริง | ง่ายกว่า แต่ถ้า parser พังเพราะ HR เปลี่ยนหน้าเว็บ ข้อมูลหายทั้งคลัง |

**งาน (A):**
1. Migration `V49__kku_doc_retired.sql` — `ALTER TABLE kku_regulation_docs ADD COLUMN retired_at TIMESTAMP`
2. ซิงก์**ครบทั้งสองหน้า**เท่านั้น: เอกสารที่ไม่เจอ → `retired_at = now()`, เจออีก → `NULL`
3. **ด่านกันพัง:** ถ้าจะถอดเกิน 30% ของที่มีอยู่ในรอบเดียว → ไม่ถอด, บันทึกเป็นซิงก์ไม่สำเร็จ + แจ้งเตือนแอดมิน ("หน้าเว็บ HR อาจเปลี่ยนรูปแบบ")
4. กรอง `retired_at IS NULL` ใน `getGroupedDocuments`, `getDocumentsByAudience`, `KkuDocumentFileService.find`, `SearchDocumentLoader` (ตัว reconcile ลบออกจากดัชนีเอง)
5. ข้อความผลซิงก์เพิ่ม "ถอดออก N รายการ"

**ต้องตัดสินใจ:** ถอดทันทีในรอบแรกที่ไม่เจอ (★) หรือรอไม่เจอ 2 รอบติด (ซิงก์รายเดือน = ช้าไปอีกเดือน)

**เทส:** ถอดเมื่อซิงก์ครบ, ไม่ถอดเมื่อหน้าใดหน้าหนึ่งพัง, ด่าน 30%, กลับมาเมื่อ HR ใส่คืน, ไม่ขึ้นในหน้าคลังและผลค้นหา

**ขนาดงาน:** ~2 ชม.

## 6. แจ้งเตือนอายุเกิน 180 วันถูกลบแม้ติดดาว

**ตอนนี้:** `NotificationRepository.deleteAncientNotificationsBefore` = `DELETE … WHERE createdAt < :cutoff` — ลบทุกอย่าง ไม่ดูดาว/สำคัญ/ยังไม่อ่าน
แจ้งเตือนไม่อยู่ในตารางระยะเก็บของ ISMS (`docs/ISMS/04-asset-inventory.md`) จึงไม่ติดข้อกำหนดเรื่องต้องลบ

| ทางเลือก | ผล |
|---|---|
| ★ **A. ไม่ลบที่ติดดาว** | เพิ่ม `AND n.isStarred = false` — ผู้ใช้ติดดาว = ตั้งใจเก็บ |
| B. ไม่ลบที่ติดดาวและที่ "สำคัญ" | "สำคัญ" ระบบตั้งให้เอง (เช่นคำขอลงนาม) — จะสะสมไม่จำกัด ไม่แนะนำ |
| C. ติดดาวเก็บนานขึ้น (เช่น 2 ปี) | มีเพดาน แต่ต้องอธิบายผู้ใช้ |

**บัคข้างเคียงที่เจอ:** ถังขยะลบตาม `createdAt` ไม่ใช่วันที่ลบ (`deleteDeletedNotificationsBefore`) → แจ้งเตือนอายุ 100 วันที่เพิ่งลบวันนี้ หายจากถังในรอบล้างคืนนี้เลย แทนที่จะอยู่ในถัง 60 วันตามที่ตั้งไว้
แก้ได้ด้วยคอลัมน์ `deleted_at` (`V50`) ตั้งค่าตอนลบ แล้วถังขยะนับจากวันนั้น (แถวเก่าที่ว่างใช้ `createdAt` เหมือนเดิม) — ~1 ชม. ทำพร้อมกันได้

**ข้อมูลเดิม:** ที่ลบไปแล้วกู้จากระบบไม่ได้ (backup `pg_dump` เก็บ 14 วัน)

**เทส:** ติดดาวอายุ 200 วันไม่ถูกลบ, ไม่ติดดาวถูกลบ, (ถ้าทำ) ถังขยะนับจาก `deleted_at`

**ขนาดงาน:** A ~20 นาที (+ `deleted_at` ~1 ชม.)

## ภาคผนวก: SQL ตรวจขนาดปัญหา (PostgreSQL, อ่านอย่างเดียว)

**Q1 — เอกสารที่ 7 ที่ระดับไม่ตรงกับคะแนนรวม (ข้อ 2a)**
```sql
SELECT r.request_code, r.current_status, d.id AS doc_id, d.is_draft,
       d.json_data::jsonb ->> 'scorex'            AS total,
       d.json_data::jsonb ->> 'eval_result_level' AS stored_level
FROM academic_document d
JOIN academic_request r ON r.id = d.request_id
WHERE d.document_type = 7
  AND COALESCE(d.is_deleted, false) = false
  AND (  (d.json_data::jsonb ->> 'scorex' = '56.00' AND d.json_data::jsonb ->> 'eval_result_level' <> 'ชำนาญ')
      OR (d.json_data::jsonb ->> 'scorex' = '71.00' AND d.json_data::jsonb ->> 'eval_result_level' <> 'ชำนาญพิเศษ')
      OR (d.json_data::jsonb ->> 'scorex' = '86.00' AND d.json_data::jsonb ->> 'eval_result_level' <> 'เชี่ยวชาญ'));
```

**Q2 — คู่ผลงานซ้ำ Scopus กับแหล่งอื่น ด้วย DOI (ข้อ 2b)**
```sql
SELECT s.fs_user_id, LOWER(s.doi) AS doi, s.id AS scopus_row, h.id AS harvested_row, h.data_source,
       (SELECT COUNT(*) FROM position_request_publication l WHERE l.publication_id IN (s.id, h.id)) AS links
FROM scopus_publication s
JOIN scopus_publication h
  ON h.fs_user_id = s.fs_user_id AND LOWER(h.doi) = LOWER(s.doi) AND h.id <> s.id
WHERE s.data_source = 'SCOPUS' AND h.data_source <> 'SCOPUS' AND s.doi IS NOT NULL
ORDER BY s.fs_user_id;
```

# แผนการพัฒนา: ปุ่มเลือกงานวิจัยให้ครบทุกกลุ่ม + ผูกผลงานกับคำร้อง + กติกาห้ามยื่นซ้ำ

**ปิด GAP-10, GAP-11/12 และ GAP-13** จาก `HRCP-KKU-Academic/docs/GAP-REPORT-flow-vs-implementation.md`

##  ภาพรวมและปัญหา (Context & Problem)

อาการที่ผู้ใช้รายงานมาตรง ๆ สองข้อ:

1. *"งานวิจัยตอนขอตำแหน่งยังไม่มีให้เลือกเลย"* — กล่องรับผลงาน 11 กลุ่มในแบบ ก.พ.ว.มข.03 มีปุ่ม
   "เลือกจาก Scopus" เพียง 3 กลุ่ม และ **ส่วนของผู้ช่วยศาสตราจารย์ ซึ่งเป็นส่วนที่ผู้ยื่นส่วนใหญ่ใช้
   ไม่มีปุ่มแม้แต่ปุ่มเดียว** ผู้ยื่นจึงสรุปว่าระบบไม่มีฟีเจอร์นี้
2. *"ยื่นไปแล้วใช้ยื่นซ้ำไม่ได้"* — บังคับไม่ได้เลย เพราะระบบไม่เคยรู้ว่าคำร้องไหนใช้ผลงานชิ้นใด
   picker ขอ citation ที่จัดรูปแล้วจาก server เขียนข้อความลงช่องธรรมดา แล้ว **ทิ้ง `publication.id`
   ไว้ที่ฝั่ง browser** ไม่มีแถวใดในฐานข้อมูลผูกคำร้องเข้ากับผลงาน

และช่องโหว่ที่พบระหว่างทาง: `app.user.email` ทำสองหน้าที่ — ทั้งเป็นบัญชีที่ `AdminInitializer`
สร้างให้ตอน start และเป็นบัญชีที่มองเห็นผลงานวิจัย **ของทุกคน** ใน picker การตั้ง `USER_EMAIL`
เป็นอีเมลอาจารย์จริง (ซึ่งเป็นเรื่องปกติที่จะทำ) จึงมอบสิทธิ์ดูงานวิจัยทั้งคณะโดยไม่มีอะไรเตือน

##  เป้าหมาย (Objectives)

1. **ปุ่มครบทุกกลุ่ม (GAP-10):** ทั้ง 11 กลุ่มที่รับผลงานทางวิชาการต้องเลือกจาก Scopus ได้
2. **ผูกผลงานกับคำร้อง (GAP-11):** id ของผลงานต้องเดินทางจาก picker ไปถึงฐานข้อมูล
3. **บังคับกติกาห้ามยื่นซ้ำ (GAP-12):** ผลงานบนคำร้องที่พ้น `DRAFT` แล้วต้องหายจาก picker และถูก API
   ปฏิเสธ — ยกเว้นคำร้องที่ `REJECTED` ซึ่งคืนผลงานให้ใช้ใหม่
4. **ปิดทางลัดที่เปิดโดยไม่ตั้งใจ (GAP-13):** แยก property ของตัวเอง ปิดเป็นค่าเริ่มต้น

##  สิ่งที่ทำจริง

### 1. GAP-10 — `templates/academic/position/applicant/doc_form_1.html`

- `SCOPUS_PRESETS` จาก 3 เป็น **11 preset** ครบทุกกลุ่ม (ผศ. 3, รศ. 4, ศ. 4)
- เพิ่มปุ่ม 8 ปุ่มถัดจากปุ่ม "เพิ่ม…" ของแต่ละกลุ่ม รูปแบบเดียวกับของเดิม
  (`data-call="openScopusPreset"` — ห้าม `onclick` เพราะ CSP ปฏิเสธ inline handler)
- ค่า prefix ทุกตัวมาจากแมป `workGroups` ที่ฟอร์มใช้สร้างแถวอยู่แล้ว จึงตรงกันโดยโครงสร้าง

### 2. GAP-11 — id เดินทางจาก picker ถึงฐานข้อมูล

| ชั้น | สิ่งที่ทำ |
|------|-----------|
| `static/js/scopus_picker.js` | `fillRows()` เขียน id ลง hidden input `{titlePrefix}_scopus_id_{n}` **ที่ picker สร้างเอง**ข้างช่อง citation |
| `academic/model/PositionRequestPublication` | entity ใหม่: request, publicationId, documentType, slotIndex |
| `db/migration/V13__…` | ตาราง `position_request_publication` + unique (request_id, publication_id) |
| `PositionRequestService.syncPublicationLinks()` | แปลง key `*_scopus_id_*` เป็นแถวผูก เรียกจากทั้ง `saveDocument()` และ `saveDraft()` |

### 3. GAP-12 — บังคับกติกา

`ScopusQueryService` ถามรายการผลงานที่ผู้เรียกใช้ไปแล้ว (`findSpentPublicationIds`) แล้วกรองออกทั้ง

- `listOwn()` → สิ่งที่ picker เห็น
- `findOwnedByIds()` → สิ่งที่ `/api/my/publications/citations` ยอมคืน

### 4. GAP-13 — `app.research.universal-access-email`

ทางลัด `isUniversalAccessUser` ย้ายจาก `app.user.email` มาอ่าน key ของตัวเองที่ **ค่าเริ่มต้นว่าง =
ไม่มีใครได้สิทธิ์**

##  การตัดสินใจที่สำคัญ และเหตุผล

1. **กรอง "ผลงานที่ใช้ไปแล้ว" ในคิวรี ไม่ใช่หลัง paging** — ถ้าตัดแถวออกจากหน้าที่ฐานข้อมูลนับมาแล้ว
   `total` จะไม่ตรงกับจำนวนแถวที่ผู้ใช้เห็น คิวรีจึงรับพารามิเตอร์ `excluded` และผู้เรียกส่ง `-1L`
   เมื่อไม่มีอะไรถูกใช้ (เพราะ `NOT IN ()` ไม่ใช่ SQL ที่ถูกต้อง)
2. **รายการ "ใช้ไปแล้ว" จำกัดด้วย `applicant_id` ของผู้เรียกเสมอ** — ถ้าถามทั้งระบบ ผู้ที่ปลอม
   hidden input เป็น id ของอาจารย์ท่านอื่นจะทำให้ผลงานของท่านนั้นหายไปจาก picker ของเจ้าตัวได้
   การผูกกับเจ้าของทำให้การปลอมกระทบแค่คนที่ปลอมเอง
3. **กรองสองที่ ทั้ง list และ citations** — กติกาที่บังคับแค่ในหน้าจอไม่ใช่การบังคับ แท็บที่เปิดค้างไว้
   หรือ request ที่ประกอบเองก็เดินผ่านได้
4. **`publicationId` เป็น `Long` ธรรมดา ไม่ใช่ `@ManyToOne ScopusPublication`** — `scopus_publication`
   เป็นกระจกเงาของ feed ภายนอกที่ sync ลบ/สร้างใหม่ได้ FK จะทำให้เหตุการณ์ปกติกลายเป็น sync ล้ม
   และการ map entity ข้ามโมดูลจะทำให้ dependency วิ่งสองทาง (วันนี้ `external` → `academic` ทางเดียว)
5. **hidden input สร้างจากฝั่ง picker ไม่ใช่จาก template** — ถ้าใส่ใน template ต้องแก้ 11 กลุ่ม และ
   กลุ่มที่คนเพิ่มใหม่ลืมใส่จะเงียบหายไปโดยไม่มีอะไรฟ้อง
6. **บันทึกแถวผูกตั้งแต่ตอนเป็นแบบร่าง** — "ยังเป็นแบบร่าง" แปลว่ายังไม่ถูกใช้ ไม่ได้แปลว่ายังไม่ต้องรู้
   ว่าคืออะไร ตัวที่ตัดสินว่าใช้ไปแล้วหรือยังคือ *สถานะของคำร้อง* ไม่ใช่การมีอยู่ของแถว
7. **ล้าง id เมื่อผู้ยื่นพิมพ์ทับแถวนั้นเอง** — เอียงไปทางล็อกน้อยเกินไว้ก่อน ต้นทุนคือรายการซ้ำที่
   เจ้าหน้าที่มองเห็นได้ ดีกว่าล็อกผลงานที่ไม่มีใครเคยยื่น
8. **ไม่แตะฟอร์มฝั่งเจ้าหน้าที่** — `/api/my/publications` ผูกกับ `Principal` เสมอ เจ้าหน้าที่ที่กดปุ่ม
   จะเห็นผลงานของตัวเอง ไม่ใช่ของผู้ยื่น บันทึกเป็น **GAP-45** ไว้ในรายงาน ต้องมี endpoint
   แบบ admin-scoped ก่อน

```bash
./mvnw test -DskipTests=false     # 1,018 เทส ผ่านทั้งหมด (ข้าม 11 เทสที่ต้องใช้ Docker)
```

|-----|-----|
| `ScopusPickerCoverageTest` (5 เทส) | [YES] รวมเทสที่เคย `@Disabled` ไว้สำหรับ GAP-10 |
| `ResearchReuseLockSpec` (8 เทส) | [YES] 6 เทสกติกาที่เคย `@Disabled` + 2 เทสเส้นทางจากฟอร์มถึงตาราง |
| `MyPublicationsScopingTest` (14 เทส) | [YES] รวมเทสใหม่ที่พิสูจน์ว่าทางลัดปิดเป็นค่าเริ่มต้น |
| `MigrationOnPostgresTest` (V13) | ⬜ **ยังไม่ถูกตรวจจริง** — Docker socket บนเครื่องนี้ยังใช้ไม่ได้ |
| `ScopusPickerE2ETest` | ⬜ **ยังไม่ถูกตรวจจริง** — เหตุผลเดียวกัน |

**ที่ต้องทำต่อบนเครื่องที่มี Docker:**

```bash
./mvnw verify -Pe2e -DskipTests=false
```

จนกว่าจะรันได้ V13 และการนับปุ่มบนเบราว์เซอร์จริงยังถือว่ายังไม่ได้ตรวจสอบ

**ตรวจด้วยตาบนแอปจริง:** เข้าเป็นผู้ยื่น → เอกสารที่ 1 → เลือก "ผู้ช่วยศาสตราจารย์" → ต้องเห็นปุ่ม
3 ปุ่ม → เลือกผลงาน → บันทึก → ส่งคำร้อง → เปิด picker อีกครั้ง ผลงานนั้นต้องหายไป → ให้แอดมิน
เปลี่ยนสถานะเป็น "ไม่รับคำร้อง" → ผลงานต้องกลับมา
